1. 通信接口选型：REST vs WebSocket

在开发基于 Qt（桌面端或嵌入式 Linux 触控屏端）的 Klipper 控制界面时，Moonraker 同时提供了 HTTP REST 与 WebSocket 两套接口。合理划分两者的使用边界可以显著简化客户端状态管理。

接口类型 适用场景 典型端点 / 方法
HTTP REST 大文件传输、静态资源拉取、一次性状态查询 POST /server/files/upload、G-code 缩略图下载
WebSocket (JSON-RPC 2.0) 实时温度/进度推送、高频状态同步、低延迟控制指令 printer.objects.subscribe、printer.gcode.script、printer.emergency_stop

对于需要持续展示喷头温度、热床温度、打印进度与运动坐标的 UI 界面，应以 WebSocket 长连接 为核心，仅在上传切片文件或下载预览图时使用 QNetworkAccessManager 发起 HTTP 请求。

2. QWebSocket 连接管理与保活

3. JSON-RPC 请求映射与消息分发

Moonraker 的 WebSocket 通信严格遵循 JSON-RPC 2.0 规范：

  • 带 id 的消息：属于客户端发起的请求及其对应的响应。
  • 不带 id 的消息：属于 Moonraker 主动下发的事件通知（如 notify_status_update、notify_klippy_ready）。

4. 状态订阅与增量数据合并

订阅对象时，建议只请求 UI 实际展示的字段，避免订阅过多无关属性造成解析开销。

在 ViewModel / Controller 层接收 statusUpdated(diffStatus) 时，需要注意两件事：

  1. 增量合并：每次推送只包含发生变化的字段，必须按 对象名 -> 属性名 合并到本地状态缓存中，不可直接覆盖整个状态对象。
  2. UI 刷新节流：若控制端运行在性能有限的 ARM 嵌入式屏端，建议将高频属性（如温度曲线采样）通过 QTimer（如 500ms）批量触发界面重绘，避免频繁触发 QML 属性绑定或 QWidget::update()。

5. 关键控制接口注意事项

5.1 阻塞型 G-code 与急停隔离

调用 printer.gcode.script 执行包含阻塞等待的指令（如 G28 回零、M109 S210 等待升温）时，Moonraker 会在该指令执行完毕后才返回 JSON-RPC 响应。

因此：

  • 不要在客户端设置过短的 RPC 超时时间来判定 printer.gcode.script 失败。
  • 急停指令（printer.emergency_stop）必须独立发送，不能与普通 G-code 放入同一个串行等待队列，否则在升温或回零卡住时将无法及时触发急停。

5.2 Klippy 重启后的状态同步

当用户执行 FIRMWARE_RESTART 后，WebSocket 连接本身不会断开，但 Klippy 进程会重启并清空所有订阅关系。客户端必须监听 notify_klippy_ready 通知并重新调用 printer.objects.subscribe，才能恢复后续状态推送。
