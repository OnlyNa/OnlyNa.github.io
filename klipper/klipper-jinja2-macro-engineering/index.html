1. Jinja2 模板的求值时机与执行模型

在 Klipper 中，[gcode_macro] 并非像常规编程语言那样逐行解释执行，而是分为两个严格解耦的阶段：

  1. 模板渲染阶段：当宏被调用时，Klipper 首先将整个 gcode: 字段作为 Jinja2 模板一次性渲染为纯文本 G-code 序列。此时模板中引用的所有 printer.* 状态对象，均为宏开始执行那一刻的快照。
  2. 指令执行阶段：模板渲染完成后，生成的纯文本 G-code 才会交由 Klipper 的 G-code 分发器逐行执行（如归零、等待升温、移动轴等）。

1.1 经典陷阱：阻塞指令后读取旧状态

由于 Jinja2 在第一阶段已经求值完毕，在同一个宏内先下发等待升温指令 M109，再通过模板表达式读取喷头温度，拿到的是升温前的旧值：

同理，在宏内执行 G28 归零后立即通过 {{ printer.toolhead.homed_axes }} 判断归零状态，也会得到未更新的结果。

1.2 正确解法：拆分子宏与 delayed_gcode

要读取阻塞指令或运动执行后的最新打印机状态，必须将后续逻辑拆分为独立的执行单元，利用延迟渲染让 Klipper 在前序指令完成后重新进入一次模板求值周期：

  • 方式一：拆分子宏。在主宏执行完 M109 或 G28 后，调用另一个独立宏 _AFTER_HEAT_CHECK，子宏被调用时才会触发新的 Jinja2 渲染。

2. 参数解析与状态存储机制

Klipper 宏系统支持从调用传参、内存运行时变量到配置文件落盘持久化三种不同生命周期的数据管理方式。

2.1 三类数据载体对比

存储方式 作用域与生命周期 重启后是否保留 典型应用场景
params 字典 仅限当前宏单次调用 否 接收切片软件或手动传入的温度、速度、坐标参数
variable_* + SET_GCODE_VARIABLE 宏对象实例级内存状态 否（RESTART 清零） 记录跨宏共享的暂停位置、标志位、挤出长度

3. 原生命令覆写与状态隔离

实际工程中经常需要对 PAUSE、RESUME、CANCEL_PRINT 或 M600 等命令进行增强。覆写原生或第三方模块注册的 G-code 时，必须同时处理好防递归与运动状态隔离。

3.1 rename_existing 防递归机制

当宏名与已有命令重名时，配置 rename_existing 会将原命令重命名为指定别名。宏体内必须调用重命名后的别名，绝不能再次调用原名，否则会触发无限递归导致栈溢出：

3.2 SAVE_GCODE_STATE / RESTORE_GCODE_STATE

切片生成的 G-code 对绝对/相对坐标模式（G90/G91）、绝对/相对挤出模式（M82/M83）以及当前进给速度（F）高度敏感。宏内只要修改了这些模态状态，就必须在首尾配对使用状态栈指令：

  • SAVE_GCODE_STATE NAME=<name>：压入当前坐标、模态标志、速度倍率与挤出倍率。
  • RESTORE_GCODE_STATE NAME=<name> MOVE=1 MOVE_SPEED=100：恢复模态状态；当传入 MOVE=1 时，自动将喷头移回保存时的 XYZ 坐标，避免恢复打印时撞件或错位。

4.2 Section 合并与 SAVE_CONFIG 优先级规则

模块化拆分时必须遵循 Klipper 配置解析器的两条核心规则：

  1. 同名 Section 后向覆写：同一 [section] 在不同文件或同一文件内多次出现时，Klipper 会将其键值合并，后加载的配置项覆盖先加载的同名键。利用这一特性，可以在 printer.cfg 底部覆写通用宏包中的个别默认参数，而无需直接修改原宏文件。
  2. SAVE_CONFIG 区块必须保留在主文件：执行 PID_CALIBRATE、BED_MESH_CALIBRATE 或 Z_OFFSET_APPLY_PROBE 后执行 SAVE_CONFIG 时，Klipper 会将参数写入 printer.cfg 末尾的 #*# <---------------------- SAVE_CONFIG ----------------------> 注释块，并在加载时以最高优先级覆写对应 section。不要手动把 #*# 区块移动到被 [include] 引入的子文件中，否则下次执行 SAVE_CONFIG 会因找不到原始生效位置而报错或覆盖失败。
